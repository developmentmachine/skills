# Plugin 幻灯提纲

页码给 [03-讲稿.md](03-讲稿.md) 用。第 1–7 页基础，第 8–13 页进阶，第 14–20 页高级。

---

## 第 1 页 · 标题

**Plugin：用标准 manifest 打包可选的 skill 和 MCP**

格式：Agent Plugins 1.0.0。使用示例：ChatGPT 与 Codex。

---

## 第 2 页 · 盒子里有什么

| 组件 | 它是什么 |
| --- | --- |
| Skill | 某件任务的手册：何时做、按什么步骤、交付长什么样 |
| MCP | 实时数据、身份与权限、受控动作 |
| Plugin | 带标准根 manifest 的自包含目录，组件按固定位置发现 |

Skill 的写法不变。插件多出来的是清单和固定目录。可以只有 skill、只有 MCP、两者都有，也可以没有组件。

---

## 第 3 页 · 基础：什么时候才打包

直接发 skill 目录：只有一份手册，就在当前项目或个人技能目录里用。

打成插件：这些东西要一起安装、一起分享。

- 好几份相关 skill
- skill 加上它依赖的 MCP
- 要出现在 ChatGPT / Codex 的插件目录里

只连接单个 MCP 服务：可以使用该客户端的原生配置，不必打插件。

按 Agent Plugins 格式分发：仍需根 `plugin.json`；标准 `mcp.json` 不能单独替代它，也不保证与客户端原生配置同形。

---

## 第 4 页 · 基础：最小目录

```text
hello-plugin/
├── plugin.json
└── skills/
    └── hello/
        └── SKILL.md
```

`skills/`、`mcp.json` 都是可选的。只含合法 manifest 的空包也符合格式，但不提供任务能力。

客户端只把 `skills/` 的**直接子目录**当成 skill，不往更深处递归找。

---

## 第 5 页 · 基础：清单只要求两字段

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "hello-plugin"
}
```

`name`：1–64 字符，只含小写字母、数字、连字符和点。不能以连字符或点开头结尾，不能出现 `--` 或 `..`。

`plugin.json` 不能把 skill 改放到别的路径，也不能内联一份 skill。

非致命例外：未知顶层字段、非对象 `extensions`，报告并忽略。其他清单错误拒绝整包。

---

## 第 6 页 · 基础：装上之后怎么用

ChatGPT 与 Codex 共用公开插件目录。

1. 打开 Plugins，安装。
2. 需要外部服务时，按提示连接。有的在安装时登录，有的在第一次使用时登录。
3. **新开**对话。
4. 直接说任务，或输入 `@` 点名这个插件、或其中某一份 skill。

Codex CLI：`/plugins`，从已配置的 marketplace 安装，然后新开一轮会话。

IDE 扩展里没有插件。标成 Desktop only 的，要在 ChatGPT 桌面应用里安装。

## 第 7 页 · 基础示例

打开 `examples/plugins/01-basic/hello-plugin/`。

现场只看两件事：

- `plugin.json` 的 `$schema` 和 `name`
- `skills/hello/SKILL.md` 的 `name` 与目录名一致

这是最小 Skill 插件示例。它还没有工具；不是所有合法插件都必须带 skill。

## 第 8 页 · 进阶：一个盒子，多份手册

```text
status-pack/
├── plugin.json
├── mcp.json
└── skills/
    ├── collect-activity/
    │   └── SKILL.md
    └── write-brief/
        └── SKILL.md
```

两份 skill 各自有 description。用户说「拉活动」时选中第一份，说「写简报」时选中第二份。插件只负责让它们一起被安装。

---

## 第 9 页 · 进阶：流程和工具分开

| 写在 skill 里 | 写在 MCP 里 |
| --- | --- |
| 顺序、SQL 模板、验收规则 | 服务连接与实际工具调用 |
| 缺字段时停下来问 | 工具能读或写哪些系统 |
| 简报的段落和禁区 | 由客户端与服务处理认证、授权 |

例子：账户活动写成客户简报。MCP 取出活动，Skill 规定结构及缺口处理。SQL 可以写在 Skill；能否执行，取决于可用工具和授权，不由说明文字决定。

没有外部系统的流程，插件里可以只有 skill。跨对话、还没写进手册的事实用 memory，不写进这个包。第一期第 7 页有完整边界。

---

## 第 10 页 · 进阶：传输写在 type 上

每个服务一个条目，`type` 必填。

| type | 用途 |
| --- | --- |
| `stdio` | 本机进程。`command` 是一个可执行名，或 `./` 开头的包内路径 |
| `streamable-http` | 当前的远程 MCP |
| `sse` | 旧式 HTTP+SSE，可选 |

首次连接必须使用声明的 `type`。后续回退行为不由规范规定，也未被规范禁止；插件不能依赖未约定的回退。

非本机的 `url` 使用 HTTPS。`headers` 和 `env` 里不放密钥。

---

## 第 11 页 · 进阶：两个路径变量

客户端启动 stdio 进程时注入：

| 变量 | 指向 | 适合放 |
| --- | --- | --- |
| `PLUGIN_ROOT` | 插件根目录 | 随包发布的脚本、配置 |
| `PLUGIN_DATA` | 该安装实例的可写目录，更新后仍在 | 缓存、依赖、生成文件 |

只在 `args`、`env` 的值、`cwd` 里展开这两种占位符。`command` 不展开。

不写 `cwd` 时，工作目录就是插件根。

---

## 第 12 页 · 进阶：坏掉的部分不拖垮整包

这些情况只跳过出问题的那一块：

- 某份 `SKILL.md` 不合格
- `mcp.json` 整体无效（这时整个 MCP 停用，skill 仍加载）
- 某一个 server 条目无效、传输不被支持、或进程起不来

`plugin.json` 缺 `$schema`、缺 `name`，或必填字段类型不对：整包拒绝，组件都不加载。

## 第 13 页 · 进阶示例

打开 `examples/plugins/02-intermediate/status-pack/`。

- `collect-activity` 写的是调用顺序和缺口处理
- `write-brief` 写的是交付格式
- `mcp.json` 声明一个 `stdio` 服务
- `bin/activity` 会立刻失败

用来说明：服务连不上时，两份 skill 的文件仍然是这个插件的有效部分。

这个目录用来看形状和失败隔离。安装后不会得到活动数据。现场不要用它证明安装成功。

## 第 14 页 · 高级：可移植核心就这两样

v1 只规定 skill 和 MCP 的位置。

钩子、斜杠命令、子代理、规则、语言服务、自定义界面，留在客户端扩展里。

规范不管：安装器、市场协议、权限模型、沙箱、签名和来源验证。这些由 IDE、CLI、企业平台各自实现。

---

## 第 15 页 · 高级：反向域名是逃生口

```text
reports-plugin/
├── plugin.json          # extensions.com.example.client
├── skills/summarize/SKILL.md
├── mcp.json
└── com.example.client/  # 只有认这个名字的客户端会读
    └── README.md
```

不认识 `com.example.client` 的客户端忽略这段配置和这个目录。可移植的 skill 与 MCP 照常加载。

名空间用自己控制的域名倒写，并保持稳定。

这里的两份传输都是声明。`bin/validate` 会故意失败。`https://mcp.example.com/mcp` 不是这门课的服务。安装后不会得到指标数据。

## 第 16 页 · 高级：一个标准入口，OpenAI 扩展放里面

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "status-pack",
  "extensions": {
    "com.openai": {
      "interface": {
        "displayName": "账户活动",
        "shortDescription": "收集活动与生成简报"
      }
    }
  }
}
```

身份与版本仍在根上。OpenAI 展示、已注册 MCP 映射、钩子设置放在 `extensions.com.openai`；不另写一份清单。

`skills/` 与 `mcp.json` 仍按固定位置发现。不支持 OpenAI 扩展的客户端忽略该名空间。

## 第 17 页 · 高级：钩子与自定义界面

Codex 钩子是生命周期命令，例如会话开始、工具调用前后。非托管钩子按当前内容的哈希信任后才运行。CLI 里用 `/hooks` 查看。

插件自带的钩子：

- 与其他钩子来源一起加载
- 仅支持手动安装到 Codex desktop 的插件
- **含钩子的插件不能进入公开插件目录**
- 在网页上安装，不会把钩子脚本部署进执行环境

自定义 ChatGPT 界面做在 MCP 集成上，不做成 `plugin.json` 的一个字段。

---

## 第 18 页 · 高级：分发是另一层

| 层 | 它解决什么 |
| --- | --- |
| 发现 | 客户端询问「这个任务有什么资源」 |
| 目录条目 | 一条记录指向插件、skill 或 MCP |
| 打包 | 本讲的目录格式 |
| 运行 | Agent Skills 与 MCP 各自的协议 |

可以只发插件、不做目录；也可以只给目录条目、里面不是插件；也可以只用 skill、不打插件。

ChatGPT / Codex：符合公开发布要求的插件可进入两边共用的目录；含钩子的插件不适用。仓库或个人用 marketplace 清单管理来源，例如 `.agents/plugins/marketplace.json`。

---

## 第 19 页 · 高级：版本、路径、密钥

- `$schema` 是协议版本。`plugin.json` 和 `mcp.json` 必须同一版。对不上时，MCP 停用，skill 仍可加载。
- `version` 是当前这份目录的标签。客户端可以拿它看有没有更新、缓存旧不旧，也可以不读。加载时不按它挑选。
- 建议语义化：主版本是不兼容变更，次版本是向后兼容的新行为，修订号是修正。不像语义化版本，不能因此拒绝整包。它不启动替换，也不证明文件变了。
- 换版本是客户端换掉这份目录。升和降在规范里是同一种替换。`PLUGIN_DATA` 保留。里面的 skill 没有单独的版本号。
- 包内相对路径以 `./` 开头，解析后必须留在插件根内。符号链接指到根外会被拒绝。
- `headers`、`env` 是包里的可见文本。密钥由客户端保管，不写进插件文件。

---

## 第 20 页 · 带走

1. 基础：插件是带 `plugin.json` 的目录；一份 skill 要分享时再打包，装上后新开对话，直接说或 `@` 点名。
2. 进阶：skill 写流程和查询模板，MCP 提供实际工具；说明不授予执行权限，一条服务失败也不阻断其他合法组件。
3. 高级：可移植的只有 `skills/` 和 `mcp.json`；钩子、界面和私有配置进反向域名扩展。
