# Plugin 讲稿

页码对应 [02-幻灯提纲.md](02-幻灯提纲.md)。括号里是动作。

这一讲假定第一期已经讲过三层加载。这里不再重讲 `description` 怎么写，只在打开示例时提醒：插件不改变 `SKILL.md` 的格式，但规定了包内发现位置：只看 `skills/` 的直接子目录，不沿用其他客户端的递归规则。

---

## 第 1 页

上一期的 skill 是一本手册。这一期的 plugin 是带标准清单的盒子，可以装手册，也可以装 MCP 配置。只有 skill、只有 MCP、两者都有，都成立；没有组件的合法空包也成立，只是它不提供任务能力。

格式叫 Agent Plugins，现在是 1.0.0。维护者里有 Amazon、Cursor、Microsoft、OpenAI、Vercel，Google 后来加入。今天讲的使用，以 ChatGPT 和 Codex 已经写明的安装和调用为准。某个 IDE 有没有开始读这个目录，以那个产品当时的文档为准，不要从「它是维护者」推成「它今天一定能装」。

---

## 第 2 页

三行就够。

Skill 仍然是任务手册。名字和描述负责被选中，正文里是步骤、模板和禁区。

MCP 负责连出去：读邮件、查表、发一条受控的写入。它带身份和权限。

Plugin 把它们放进约定好的位置，让安装动作一次完成。装完以后，模型看到的还是那些 skill 的描述，工具还是 MCP 暴露的工具。插件本身不是第三种提示词。

---

## 第 3 页

基础使用的第一个判断是：要不要打包。

团队里已经有一份 PR 描述 skill，放在项目的技能目录里，同事克隆仓库就能用。这种就停在 skill。

要打包的典型情况是：PR 描述 skill、读取 CI 或议题的 MCP、描述模板必须一起出现。少装一个，流程就断。或者你希望它出现在 ChatGPT 和 Codex 的插件目录里，让没克隆你仓库的人也能安装。

反过来，只把一个 MCP 接到一个客户端，可以用那个客户端的原生配置，不一定打包。这里说的是客户端自己的配置，不是把标准 `mcp.json` 单独交过去就保证能读。若按 Agent Plugins 格式分发，即使只有 MCP，也必须有根 `plugin.json`。插件赚的是「这些零件按同一包格式交付」。

---

## 第 4 页

（打开基础示例的目录树，先不要进文件。）

最小插件是一个文件夹。根上必须有 `plugin.json`。有 skill 就放在 `skills/` 下面，每个 skill 一个子目录，里面一份 `SKILL.md`。

两个容易写错的发现规则。

第一，没有 `skills/` 不是错误。没有 `mcp.json` 也不是错误。客户端加载存在且合法的部分。

第二，只看 `skills/` 的下一层。你不能像在 Cursor 项目里那样，再套一层 `skills/writing/pr-description/SKILL.md` 就指望插件规范把它找出来。分类目录要放在插件根之外，或者每个 skill 直接放在 `skills/` 下。

---

## 第 5 页

清单是闭的。允许的顶层字段就那些：`$schema`、`name`，以及版本、描述、作者、主页、仓库、许可证、关键词、`extensions`。

必填是前两个。`$schema` 写死这一版的地址，客户端用它选择本地已经实现的校验规则，加载时不会去网上把 schema 下载下来。

名字比 skill 的名字宽一点：可以有点，所以 `acme.tools` 合法。大小写、首尾的连字符或点、连续的 `--` 和 `..` 不合法。

有两个非致命例外：未知顶层字段，以及不是对象的 `extensions`。客户端报告并忽略它们，其他部分仍符合要求时继续加载。除此之外的清单错误才是致命的，整包不用。作者仍应修正这些违规，不能把「继续加载」当成字段可以随便写。所以不要把 MCP 地址塞进 `plugin.json`；地址的位置是根上的 `mcp.json`。

---

## 第 6 页

基础使用的后半段是安装和调用，先讲 ChatGPT 与 Codex，因为这两边的目录是公开写明的。

两边看同一份公开插件目录。网页、桌面、移动上的 Chat 和 Work 可以用；Codex 在 ChatGPT 桌面应用里可以用。移动端能用账号里已经可用的插件。有的插件标了只能桌面安装，网页上能看见，装和用要到桌面应用。

安装步骤就四下：找到、加上、按提示连接外部账号、新开对话。连接有的发生在安装时，有的拖到第一次调用。Sign in with ChatGPT 若出现，分享的是名字、邮箱和头像；插件还要再单独批它申请的权限。

调用有两条。说人话：「总结今天未读的邮件」。或者 `@` 点名插件，或点名它里面的某一份 skill。想指定时用第二条。

Codex CLI 是 `/plugins`，从 marketplace 安装，装完要新开一轮。IDE 扩展这条链路没有插件，要到桌面应用或 CLI。

---

## 第 7 页

（打开 `hello-plugin/plugin.json` 和 `skills/hello/SKILL.md`。）

这就是最小 Skill 插件示例。Skill 的 `name` 是 `hello`，目录也是 `hello`，正文只规定打招呼。清单必填是 `$schema` 和 `name`，示例额外写了 description。只有清单也符合格式，只是不能拿它演示任务能力。

它能被当成插件安装。它不能查询任何系统。下一档才加工具。

如果现场有人问「我把它复制到 `.cursor/skills` 行不行」：那是在用第一期的技能目录，不是在安装插件。复制时要复制的是 `skills/hello/`，不是整个插件根。插件根上的 `plugin.json` 不是 `SKILL.md`。

---

## 第 8 页

进阶使用从「一次安装多份手册」开始。

`status-pack` 里有两份 skill。收集活动是一件事，写成简报是另一件事。描述不同，模型可以只启用其中一份。

插件没有把两份手册合并成一个更大的提示。它只保证安装 `status-pack` 的人同时得到两份。这和第一期说的「复杂流程拆成小 skill」是同一件事，只是现在有了共同的安装单位。

---

## 第 9 页

进阶里最重要的分工，OpenAI 的插件文档写得很直。

MCP 给出活的信息和受控动作，包括认证和授权。Skill 给出围绕这些工具的流程：什么时候调、按什么顺序、结果缺了一截怎么办、最后必须包含哪些段。

四个对得上的例子：账户活动变客户简报；项目数据里找风险再写状态；搜索和抓取合成带来源的调研；把团队的写作标准套到 MCP 返回的结果上。

Skill 也可以不带 MCP。纯格式、纯检查清单，插件里只有 `skills/` 完全成立。SQL 示例、查询模板、转换规则可以写在正文或参考文件里；但写了查询不等于有工具和授权去执行。真正执行依赖 MCP、CLI 或脚本等可用工具。`mcp.json` 描述 MCP 服务如何启动或连接，不是放 SQL 的位置。真实令牌和密码不写进 Skill 或连接配置，交给客户端的认证与凭据存储。

Memory 也不进这个包。跨对话还成立、又还没写成手册的偏好，留在记忆里。它一旦变成团队约定，晋升进 skill，而不是写进 `plugin.json`。第一期第 7 页讲过这些边界。这期没听过的房间，先投那一页再继续。

---

## 第 10 页

写标准 `mcp.json` 时，每个服务显式写 `type`，不能靠字段长得像不像来猜测本地进程还是远程 HTTP。首次连接必须使用声明的传输。失败后是否回退由客户端决定，规范没有规定，也没有禁止；插件不能把未约定的回退当成一定可用。

`stdio` 的 `command` 是一个词。`npx` 可以。`./bin/activity` 可以。`python app.py --port 8080` 这一整串不行，参数放 `args`。包里自带的可执行文件用 `./` 相对路径，不要赌客户端的 `PATH` 里有没有它。

远程用 `streamable-http`。`sse` 是旧传输，客户端可以不实现。本机地址可以用 HTTP，`localhost` 或回环 IP。其他主机用 HTTPS。URL 里不带用户名密码，也不带片段。

`headers` 谁都能在仓库里看见。租户名这种公开标记可以写。访问令牌不写。授权失败算这个服务没连上，不算整份清单非法。OAuth 怎么弹窗，规范交给客户端。

---

## 第 11 页

进程跑起来以后，需要知道包在哪、数据写到哪。

`PLUGIN_ROOT` 是插件根的绝对路径。脚本和只读配置用它。

`PLUGIN_DATA` 是客户端选的目录，这个已安装实例专用，可写，插件升级时保留，卸载时客户端可以删。依赖、缓存、生成出来的文件放这里。不要把它们写回 `PLUGIN_ROOT`，下一次更新会把包内容换掉。

占位符只替换 `${PLUGIN_ROOT}` 和 `${PLUGIN_DATA}`，而且只替换一次，替换出来的文本里如果再出现这两个字，不会继续展开。不认识的 `${...}` 原样留下。`command` 这个字段完全不替换。

所以包内程序写成 `./bin/activity`，参数里需要绝对路径时才写 `${PLUGIN_ROOT}/config/db.json`。

---

## 第 12 页

进阶使用要建立的预期是：局部失败。

一份 skill 的 frontmatter 写错了，跳过这一份，下一份还在。一个 server 的 `type` 这个客户端不支持，跳过这一条，别的 server 还连。进程启动失败、认证失败、握手失败，同样只影响这一条。

`mcp.json` 不是合法 JSON，或者它声明的规范版本和 `plugin.json` 不一致：这个插件的 MCP 全部停用，skill 继续。版本写错不会让手册一起消失。

整包拒绝只有清单这一层：没有 `$schema`，没有 `name`，名字不合法，或者必填字段类型不对。这时客户端不该再去跑里面的组件。

设计理由是：一个写 PR 说明的插件不该因为 CI 今天连不上，就连描述格式一起不可用。

---

## 第 13 页

（依次打开两份 SKILL.md、mcp.json、bin/activity。）

`collect-activity` 只写顺序：要哪些字段、缺了怎么停、拿到记录之后交给哪一份格式。它不包含服务器地址。

`write-brief` 只写四段输出。它可以被单独点名，即使用户已经自己把活动贴进对话。

`mcp.json` 是合法形状。`bin/activity` 启动后马上以非零退出，并在错误输出里说明自己不是 MCP 服务。这是分享用的占位，避免现场真的去连一个系统。

你若把这个目录交给一个符合规范的客户端，预期是：activity 这一条报连接失败；`collect-activity` 和 `write-brief` 仍作为该插件的 skill 被发现。现场不必真的安装，把这个预期讲清楚即可。

这个目录用来看形状和失败隔离。安装后不会得到活动数据。不要用它证明安装成功。

---

## 第 14 页

高级使用的边界：不要把插件规范理解成「客户端的全部扩展机制」。

v1 选择 skill 和 MCP，是因为这两样在规范之外已经有自己的标准，而且多个客户端都在用。钩子、命令、代理、规则、LSP，各家形状差得远，所以留在核心外面。

同样留在外面的还有产品行为。安装按钮长什么样、企业管理员怎么审批、进程隔离到什么程度，IDE、命令行和托管平台的义务不一样。规范把这些写进后续考虑，而不是假装已经统一。

高级用户要做的，是把可移植的部分写进固定位置，把只在一个产品里有意义的部分放到扩展里。

---

## 第 15 页

（打开 reports-plugin 的目录。指扩展目录时，也指出 `mcp.json` 里的两份传输声明。）

这里的两份传输都是声明。`bin/validate` 启动后马上失败，并说明自己不是 MCP 服务。`https://mcp.example.com/mcp` 不是这门课的服务。安装后不会得到指标数据。现场用这个目录看形状，不要用它证明安装成功。

逃生口有两个位置，用同一个反向域名。

清单里是 `extensions` 对象，键是名空间，值必须还是对象。文件则放在插件根下同名目录。可以只用其中一个。

客户端看到不认识的名空间，不校验里面的内容，直接忽略。所以你给自己的产品加钩子目录，不会把 Claude、Cursor 或其他客户端的加载弄失败。它们继续读 `skills/` 和 `mcp.json`。

名空间用你控制的域名倒过来写，例如 `com.example.client`，并且不要随版本改名。改名等于让旧客户端找不到扩展。

---

## 第 16 页

这一页只保留一套格式：标准根 `plugin.json`。身份、版本和描述仍在根上，skill 在 `skills/`，MCP 配置在根上的 `mcp.json`。不为 OpenAI 再写一份身份清单。

OpenAI 专有的展示、已注册 MCP 映射、钩子设置，放在 `extensions.com.openai`。投影里的例子只是给标准包增加显示名称和短描述，没有改组件位置，也没有新增工具。

不认识这个扩展的客户端忽略这一段，继续加载它支持的标准组件。认识它的客户端按自己的规则解释，所以「包能读」不等于「所有私有能力都可用」。

不要为了扩展而把 `name`、`version` 或 MCP 服务地址挪进名空间。扩展里的注册映射不是根 `mcp.json` 的替代品，界面和登录流程仍属于实际集成。

---

## 第 17 页

钩子是 Codex 的生命周期命令，不是 Agent Plugins 的一种组件。

它从几处一起加载：用户目录、仓库的 `.codex/`、以及已启用插件里带的钩子。高优先级配置不会把低优先级的钩子替换掉，匹配到的都会跑。非托管钩子在运行前要信任当前这份内容的哈希；改了一个字就要重新信任。CLI 用 `/hooks` 看、信任或关掉某一条。系统、MDM、云端策略下发的托管钩子，用户界面里关不掉。

这里要先分安装场景和发布渠道。OpenAI 的打包文档把插件生命周期钩子限定为手动安装到 Codex desktop 的场景；含钩子的插件不能进入公开插件目录。写进 `extensions.com.openai` 只是在正确位置配置它，不会解除产品限制。

在网页上点安装，也不会把钩子脚本部署到执行环境里。脚本得已经在目标机器上，企业环境可以由管理员下发。决定给谁使用之前，先查对应安装来源、执行环境和权限规则。

自定义界面同样不要写进可移植清单。需要界面时，走 MCP 那条集成自己的 UI 说明。

---

## 第 18 页

高级使用的分发，不要和打包混成一件事。

Google 的说明把四层分开：发现、目录条目、打包、运行。插件格式只占第三层。你可以发布一个没有目录条目的插件，也可以给一个单独的 skill 做目录条目，也可以完全不打插件。

落到 ChatGPT 和 Codex：公开插件发一次，进两边共用的目录。目录里分 OpenAI 提供的、工作区的、个人的。个人区能看到自己创建的和分享给自己的。工作区管理员可以从 GitHub marketplace 导入给团队。

带钩子的包不走上面这条公开发布路径，需按官方支持的手动桌面安装场景验证。不要把「在本机装得上」理解成「能进公开目录」。

自己试的时候，用一份 marketplace JSON 把多个插件列在一起。仓库级放在 `.agents/plugins/marketplace.json`，个人级放在用户目录的对应位置。每条用 `./` 相对路径指向插件文件夹。Codex CLI 可以用 `codex plugin marketplace add` 添加来源，真正的安装测试文档仍建议在 ChatGPT 桌面应用里做。

本地 marketplace 和公开目录是两种来源。前者适合开发和团队，后者才是对外一次发布。

---

## 第 19 页

最后把高级使用里会踩的三类约束放在一页。

版本有两个，都在包上，不在单份 skill 上。

`$schema` 是协议版本。两份 JSON 必须同一版，否则这份 MCP 配置作废，skill 还在。客户端不认识这个协议版本，就拒绝整包。

`version` 是作者写在当前这份目录上的标签。装上之后加载的就是这个目录，没有「选 1.2.0 再激活」。客户端可以用这个字符串判断有没有更新、缓存是否过期，也可以完全不读。建议按语义化版本写：主版本号表示不兼容变更，次版本号表示向后兼容的新行为，修订号表示修正。写得不像语义化版本，不能单凭这一点拒绝整包。作者邮箱、主页不像 URL，同样不能单独构成拒绝理由。

这个标签不证明目录里的文件变了。作者不改字符串，文件照样可以换。它也不触发升级或降级。规范没有「装到某个版本」或回滚的步骤。客户端若要换版本，就是用另一份目录替换当前这份，升和降是同一种替换。替换之后 `PLUGIN_DATA` 保留。

插件里的 skill 仍只遵守 Agent Skills。那份规范没有会被加载的版本字段。`metadata` 里的版本号只是书目。

路径：配置里的插件相对路径以 `./` 开头。`../` 逃出根目录是非法的。符号链接如果解析到根外，客户端要拒绝那条路径。这约束的是包里的文件，不是把子进程沙箱化。运行时别人传进来的路径，不由这条规则自动封住。

密钥：`env` 和 `headers` 都会进仓库、进安装包。规范写明它们不是可移植的保密机制。令牌放在客户端的登录和凭据存储里。另外，`env` 里不能自己声明 `PLUGIN_ROOT` 或 `PLUGIN_DATA`，这两个名字由客户端在套用你的 `env` 之后强制写上。

## 第 20 页

三档对应三句，和第一期的三句接得上。

基础：需要一次安装、换地方还能被找到时，在 skill 外面加 `plugin.json`。使用就是装上、新开对话、直接说或 `@`。

进阶：Skill 写流程和查询模板，工具负责实际调用。说明文字不授予权限；某个服务挂了，其他合法组件仍能加载。

高级：想带到别的客户端的，只放 `skills/` 和 `mcp.json`。钩子、界面、只给一个产品的开关，放进反向域名。规范把安装和信任留给各个产品，所以高级使用包括读那个产品自己的限制，而不只是把目录拼对。
