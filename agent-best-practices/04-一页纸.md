# Agent 可靠交付一页纸

## 先判断是否适合

一项任务适合交给 Agent，需要同时满足：

- **可验证**：知道怎样判断结果是否正确
- **可访问**：Agent 能拿到必要事实和工具
- **可控制**：错误动作可以限制、审批或回退

步骤完全固定时优先写脚本。缺少事实来源时先补数据。高风险、不可逆的最终决定保留给人。

## 六项任务契约

```text
目标：
最终要改变什么？

范围：
允许查看和修改什么？

事实：
以哪些文件、测试、日志或系统为准？

约束：
不能做什么？哪些明确不在本次范围？

完成：
哪些检查通过才算结束？

审批：
什么动作前必须停下来问？
```

任务契约不是固定提示词。缺哪一项，就补哪一项。

## 执行循环

```text
观察 → 计划 → 行动 → 检查
  ↑                    ↓
  └──── 未达标则继续 ──┘
```

- 修改前先建立基线。
- 简单、可逆、有明确测试的动作可以直接执行。
- 范围不清、高风险或不可逆的动作先给计划并等待批准。
- 一次只扩大一个可验证范围。

## 验收四问

1. 它依据了什么事实？
2. 它实际做了什么？
3. 什么证据证明结果正确？
4. 哪些内容仍未验证？

优先看真实产物：测试输出、diff、日志、文件和外部系统状态。Agent 的完成说明只是索引，不是证据。

## 跑偏时怎样恢复

1. 停止继续扩大改动。
2. 找出缺失事实或错误假设。
3. 回退无关改动。
4. 缩小成一个可验证步骤。
5. 上下文污染时，新开一轮，只带已确认事实、当前 diff 和真实错误。

工具失败就报告错误。没有运行过就写「未运行」。没有证据就写「未验证」。

## 机制怎么选

- 本次目标和临时要求：Prompt
- 持续或按范围生效的约束：Rule
- 已验证的一类重复流程：Skill
- 读取事实和执行动作：工具 / MCP
- 可能过期的跨会话状态：Memory
- 隔离上下文或并行调查：Subagent
- 按时间或事件启动：Automation
- 打包和分发 Skill、MCP：Plugin

治理贯穿所有机制：权限、审批、测试、日志和评估。

## 沉淀前检查

- [ ] 这套做法已经在真实任务中成功过多次
- [ ] 输入、输出和失败边界相对稳定
- [ ] 有可以重复运行的验收方式
- [ ] 高风险动作有审批和回退
- [ ] 自动运行时有幂等、超时、通知和人工接管

第一次成功是案例，不是标准流程。
