## 第 1 页

（标题页只停留片刻，不先解释概念。）

很多人开始用 Agent 后，第一个问题都是：「Prompt 怎么写得更好？」

但今天我想先问另一个问题：**Prompt 已经写得很清楚了，为什么 Agent 仍然可能交付失败？**

（切到第 2 页，先展示 Prompt 和 Agent 的完成说明。）

这段 Prompt 有目标、有范围，也要求运行测试。Agent 也明确告诉我们：「已经修复，所有功能正常。」

**现在，这个改动可以合并吗？**

（停三秒，让听众先判断，再显示下面四个问题。）

还不能。因为我们不知道它依据了什么、实际改了什么、测试是否真的运行，以及还有什么没有验证。

所以今天不讲一套万能提示词，也不把某个平台的按钮过一遍。我们讨论的是：**怎样让 Agent 从「会回答」，走到「能可靠交付」。**

Prompt 是任务入口，不是交付系统。可靠交付需要目标、上下文、受控行动和验证证据形成闭环。

这节课会完成一次真实的小任务。重点不是 Agent 回答得像不像专家，而是我们能不能看见它依据了什么、做了什么、怎样证明结果，以及哪里还不知道。

结束时，初学者应该能安全地交出一个任务；长期用户应该能诊断一项 Agent 工作为什么不可靠，以及应该在哪一层修。

---

## 第 2 页

（承接开场，四个问题此时已经显示。）

这不是一段明显糟糕的 Prompt。它已经写了目标、修改范围和验证要求。问题是，Prompt 只能提出要求，不能证明 Agent 确实照做。

回复没有明显语病，甚至很像一份专业汇报。但它没有提供任何可复核信息。

「优化了状态管理」可能只改了一个变量，也可能重写了一整层。「所有功能正常」可能代表跑了完整测试，也可能什么都没跑。

Agent 很擅长生成符合完成语气的文字。语言上的确定感不是事实上的确定性。

所以今天不是把 Prompt 拉得更长，而是从一句 Prompt 向外建立完整工作闭环。统一的判断标准是：没有证据，就把它当成尚未验证，而不是已经完成。

## 第 3 页

先统一三个容易混用的词。

用户 Prompt 是用户提交的那段任务请求。模型输入是某一次调用时，模型实际收到的全部内容。上下文窗口则是一次调用能够处理的有限容量，不是某一段具体文本，也不是永久记忆。

两者之间还有 Agent 宿主。它会把 System 和 Developer 指令、用户 Prompt、对话历史、被选中或加载的 Rule、Skill、Memory、检索到的事实、当前任务状态、工具定义和此前的工具结果，组装成一次模型输入。不同产品怎样选择、排序、截断这些内容并不完全相同。

（问听众：「用户 Prompt 完全相同，但工具返回了不同结果，下一轮模型输入还相同吗？」答案是不相同。）

模型根据这次输入判断下一步。它可以生成回复，也可以请求调用工具；真正打开文件、运行测试或更新系统的是宿主提供的工具。工具结果通常会被加入下一轮模型输入，让模型继续判断。

这也解释了两个现象。第一，用户 Prompt 写得很好，其他指令、错误历史或无关内容仍可能让任务跑偏。第二，模型本身不会因为“上一轮想过”就可靠地保存任务状态；连续性依赖宿主再次组装进去的上下文，以及代码、测试、计划等外部产物。

所以结果不好时，不要只问「用户 Prompt 是不是不够好」。还要检查 Agent 最终拿到了哪些事实、规则、状态和工具结果，以及宿主允许它做什么。

## 第 4 页

不是所有事情都应该交给 Agent。

第一，结果能不能验证？有测试、有结构化检查、有明确来源，比较适合。只有「做得更高级一点」，但没人能说明什么叫高级，Agent 只能猜。

第二，它能不能访问必要事实？让它判断线上故障，却不给日志、监控或读取工具，再好的模型也只能编假设。

第三，错误动作能不能被控制？读文件和创建草稿可以给较高自主度。删除生产数据、对外发送、合并发布，应该保留审批或交给确定性系统。

如果步骤固定、输入输出稳定、几行脚本就能可靠完成，直接用脚本通常更便宜、更可预测。Agent 适合处理需要判断、调查和调整的部分。

## 第 5 页

任务契约不是一段必须逐字复制的提示词，它是一张开工检查单。

目标回答最终要改变什么。范围告诉 Agent 可以看哪里、改哪里。事实说明以什么为准，避免它拿常识覆盖项目现实。

约束里既写不能做什么，也写这次明确不做什么。完成标准必须能检查。审批点说明哪些动作之前必须停下来。

最常见的问题是只给目标，不给完成标准：「修一下登录问题」。Agent 修到什么程度才停？要不要顺便重构？要不要安装依赖？每一步都只能猜。

任务契约的价值不是消除所有不确定性，而是让不确定性显形。缺事实时应该提问，达标时应该停止。

它最终可以写进 Prompt，但重点不是句式，而是这些关键信息有没有被定义。Prompt 是入口；任务契约让这个入口可执行、可停止、可验收。

---

## 第 6 页

任务契约也不等于每次都让用户重新填写六行。长期稳定的部分应该放进合适的配置层，当前任务只补这一次的变化。

平台和组织层保存权限、安全与合规底线。用户层保存跨项目成立的偏好和默认工作方式。项目层保存架构边界、标准命令、权威事实源和默认验收要求。目录层只补充某个模块独有的约束。当前任务再提供这次的目标、范围、完成标准和临时例外。

例如，「回答使用中文」可以是用户级偏好；「数据库改动必须附迁移文件」属于项目级规则；「前端组件必须跑视觉回归」可以放在前端目录；「这次只修登录超时，不重构认证模块」只属于当前任务。

放置原则是：一条要求放在能够准确覆盖它的最小稳定作用域。不要把只适用于一个仓库的要求污染所有项目，也不要让每次都成立的项目约束依赖用户反复粘贴。

发生冲突时，不能简单地说「越靠下越优先」。高权限规则不能被低权限规则覆盖，安全和审批边界不能被当前任务静默放宽；同一权限层内，更具体的作用域通常优先。目标发生变化时，要明确它是补充、暂停还是替换。

事实冲突又是另一回事。测试、文档和线上状态不一致时，不能拿指令层级替事实裁决，而要检查来源、时间和适用范围。

`AGENTS.md`、Rule、系统指令或产品配置只是承载这些层次的不同方式。具体目录和加载顺序因产品而异。克隆来的项目规则也相当于别人写给 Agent 的指令，使用前需要检查来源和信任边界。

最下面还有运行时状态：当前进度、错误输出、diff 和验证证据。它们会不断变化，应该进入状态快照或真实产物，而不是被写成长期规则。

## 第 7 页

分层原则可以跨产品复用，但承载它们的文件还没有完全统一。

项目级 `AGENTS.md` 的兼容性已经比较好。Codex、Cursor、Hermes 和 GitHub Copilot 都能原生读取，不过它们寻找父目录、加载子目录以及处理覆盖的细节并不完全一样。

Gemini CLI 默认使用 `GEMINI.md`，从用户目录、项目到子目录分层加载。它允许通过 `context.fileName` 配置一个或多个名字，所以可以让它读取 `AGENTS.md`，但不能在没有配置时假设它会读。

Claude Code 更明确：它读取 `CLAUDE.md`，不直接读取 `AGENTS.md`。如果项目希望公共规则只维护一份，可以让 `CLAUDE.md` 只写 `@AGENTS.md`，再在下面补充 Claude 专属内容。

因此，一个务实的仓库结构是把跨工具规则放在根目录 `AGENTS.md`，产品专属文件只做入口或差异补充。不要把同一份规则复制六遍，否则下一次修改就可能产生六个互相冲突的版本。

用户级配置仍然是碎片化的。Codex、Gemini、Claude、Copilot、Hermes 和 Cursor 各有自己的路径或设置。尤其要避免一个常见误解：`~/.agents/` 已被多款产品用作共享 Skill 目录，但它不是大家都会读取的全局规则目录。

最后，支持某个文件名只代表宿主可能把它装进模型输入，不代表规则一定被遵守。配置后要检查当前产品实际加载了什么；权限和不可违反的安全边界仍要由审批、沙箱、Hook 或确定性程序落实。

具体路径、优先级和官方链接放在 [06-规则文件平台对照.md](06-规则文件平台对照.md)，主线不要求背诵。

## 第 8 页

规则文件不是写完一次就不动，也不是遇到一次问题就永远追加一条。只增不减的结果，是重复、冲突和过期内容一起占用注意力，真正重要的规则反而更难被遵循。

`AGENTS.md` 是普通 Markdown，没有标准的 `version` 字段。写一个版本号不会自动改变加载行为。更可靠的版本记录是 Git commit、diff、PR 和评审历史；需要时可以用注释记录 owner 和 last-reviewed，但要明确那只是团队约定。

长度也没有跨产品统一值。Codex 默认最多合并 32 KiB 项目规则；Hermes 会按配置或模型窗口截断；Cursor、Gemini CLI 和 Copilot 没有公布统一的 `AGENTS.md` 硬上限。Claude Code 虽然读取的是 `CLAUDE.md`，官方建议每份少于 200 行。

课程用 200 行作为根规则的软预算，不把它说成 `AGENTS.md` 标准。真正要检查的是用户、项目和目录规则合并后的总量，以及关键规则能不能稳定生效。

一条规则进入长期文件前，至少回答四个问题：这个问题是否重复出现？代价是否明确？规则是否相对稳定？能否设计案例验证行为？一次偶发错误先留在任务记录里。

修改规则也要像修改代码：选择最小作用域，做一项最小改动，同时删除被替代或冲突的旧内容。然后跑代表性案例、冲突案例和失败案例，检查各产品实际加载结果，再根据证据保留、修改或回退。

有些问题根本不该写成指令。按需工作流进入 Skill，动态数字重新查询，安全底线进入权限和 Hook，可执行规范进入测试和 CI。

示例里的 `instruction-evals.md` 就是一组规则回归案例。我们评价的是 Agent 有没有采取正确行动以及证据是什么，不要求它输出某一句固定文字。

## 第 9 页

上下文不是越多越好。把整个仓库、十份文档和两年前的聊天全塞进去，会让过期信息和无关细节争夺注意力。

更稳的方式是指向事实源：问题在 `issue.md`，行为由测试定义，仓库约束在规则文件，线上状态从监控系统读取。

但能被读取的内容不等于能发号施令。网页、邮件、Issue 和日志都可能包含错误、恶意或过期的文字，要把它们当成待判断的数据。任务契约和明确适用的规则才有指令权；敏感信息也不能因为文件可读就被复制到回复或外部系统。

来源之间还可能冲突。测试、文档和线上行为说法不一致时，不要让 Agent 静默挑一个顺眼的答案。让它列出冲突、来源和时效，能按事先约定的权威顺序解决就解决，否则停下来确认。

让 Agent 先调查，再用自己的话复述当前判断。此时你检查的是：它找对了事实没有、有没有把背景误当要求、有没有隐藏假设。

Memory 适合保存偏好和历史决定，但可能过期。实时 CI 状态应该重新查询，不能以「上次记得是绿的」为准。

长任务还有一个常被忽略的问题：怎样让主线在多轮对话、中断和上下文压缩之后仍然连续。靠 Agent 记住全部聊天并不可靠，更稳的做法是维护一份可恢复状态：主目标是什么、已经完成什么、当前走到哪里、下一步是什么、还有什么阻塞。

用户负责稳定目标和验收标准，Agent 负责更新执行状态。关键决定要落到计划、文档、测试或代码中，不要只存在聊天里。方向变化时，明确说明这是补充原任务、暂停原任务，还是用新目标替换原目标。

如果 Agent 基于错误假设开始工作，不要继续围绕那个假设补故事。更新事实，然后重新判断计划。

## 第 10 页

可靠执行通常能拆成四步：观察、计划、行动、检查。

观察不是礼貌动作。修改前的失败测试、日志和当前实现，是之后判断有没有修好的基线。

计划也不是每次都要写十条。一个只改一行、能立刻运行测试、失败后容易回退的任务，可以调查后直接做。范围跨多个模块、影响外部系统或不可逆时，应该先给计划并等批准。

行动尽量一次只改变一个可验证范围。检查失败就回到观察，而不是继续扩大修改。

发送消息、创建工单、部署或修改线上配置这类外部写操作，还要形成自己的小闭环：执行前重新读取状态，必要时等待审批，使用幂等键或去重机制避免重试造成重复动作，执行后再读取真实系统确认结果。看到一次成功回复，不等于外部状态已经正确。

自主程度应该跟风险和可验证性一起提高。不是 Agent 越强，就应该给越大的不可逆权限。

---

## 第 11 页

这些机制经常被放在一起讨论，但解决的是不同问题。

Prompt 是这一次要做什么。Rule 是持续或按范围生效的约束。Skill 是做某一类任务时才需要的可复用流程。

工具让 Agent 接触真实世界。MCP 是接入工具和资源的一种方式，不等于数据库，也不保证数据天然正确。

Memory 保存跨会话状态，但不能替代权威事实源。Subagent 用来隔离上下文或并行调查，本身不会自动提高正确率；主 Agent 仍要给出清楚的委派契约并验收产物。

Automation 解决什么时候启动。自动触发一项没有停止条件、没有幂等和没有失败通知的工作，只会更快地产生不可控结果。

Plugin 是打包分发层。它能把 Skill 和工具送到客户端，不能替代运行时的验证。

## 第 12 页

（切到 `examples/login-submit/`，先展示文件树，不要先展示实现。）

我们来做完整演示。原始说法可能只有一句：「修一下重复提交，别改太多。」

这一次不把六项契约完整粘进 Prompt。根 `AGENTS.md` 保存项目长期成立的环境、行动边界、默认验证和审批要求。`src/AGENTS.md` 与 `tests/AGENTS.md` 保存各自目录的特殊约束。`issue.md` 才说明本次问题、预期和非目标。

测试输出、当前 diff 和进度不会写进规则文件，因为它们属于运行状态。用户 Prompt 只负责启动任务，并要求 Agent 在行动前从这些来源组装出六项契约。

先检查当前宿主实际自动加载了什么。有上下文查看功能就看宿主记录；没有时，不要求 Agent 猜自己的隐藏模型输入。让它明确区分：「宿主已经注入」和「为了完成任务，我后来显式读取」。

某个产品没有自动发现嵌套 `AGENTS.md`，不代表演示失败。显式读取后仍然可以继续，这正好说明文件存在、Agent 可访问和宿主已加载是三件不同的事。

最后让 Agent 用目标、范围、事实、约束、完成和审批复述契约，并给每项标注来源。这里检查的是：用户不用每次填写六行，Agent 能否把稳定默认值和当前任务正确组合起来。

注意，我们仍然没有告诉 Agent 应该改哪一行。契约规定结果和边界，不替它伪造技术结论。

## 第 13 页

（按 [05-现场练习.md](05-现场练习.md) 的演示步骤操作。）

先运行测试。修改前失败很重要：如果问题无法复现，修改后测试通过也不能证明是这次修改修好的。

然后看它读了适用规则、Issue、测试和实现。这里既检查规则来源是否真实，也检查技术判断依据的是仓库事实，而不是根据问题名称脑补。

修改后再运行同一条测试命令。命令输出要真实出现在记录里。接着看 diff，确认没有顺手重构、没有改公开接口、没有藏进无关格式化。

最后让 Agent 汇报未验证内容。例如这个示例只有单进程内存状态，没有覆盖多进程、持久化或真实 HTTP 层。主动写出这些限制，比一句「全部正常」更可信。

如果 Agent 一次没有成功，不要替它掩盖。这正好进入下一部分：怎样验收和恢复。

---

## 第 14 页

验收不需要重新做一遍 Agent 的全部工作，只问四件事。

第一，它依据什么事实？答案应该指向文件、测试、日志或系统，而不是「根据经验」。

第二，它实际做了什么？看 diff、文件列表、命令记录和外部写操作。

第三，什么证据证明结果正确？检查是否使用了与目标对应的测试，而不只是随便跑了一条绿色命令。

第四，哪些内容仍未验证？未覆盖平台、未运行检查、权限不足和残余风险都应该明确写出来。

读取了 Skill、调用了工具，只能证明过程中的一个动作发生过。它们不自动证明最后结果正确。

---

## 第 15 页

Agent 跑偏以后，最常见的错误是继续往同一个对话里塞更多指令。上下文已经有错误假设和无关修改，新指令可能只让冲突更多。

先停止扩大范围。找出最早出现偏差的地方：事实没读到、目标理解错了、测试没有覆盖，还是工具失败了。

把无关改动回退，缩成一个能在几分钟内判断对错的步骤。例如先只复现问题，不允许修改。

上下文已经很长或反复自我解释时，新开一轮。带过去的是已确认事实、当前 diff 和真实错误，不是整段争论。

任务被打断后，也不要直接说「继续」。先让 Agent 根据当前产物复述主目标、已完成内容、当前状态和下一步，确认没有偏离后再行动。连续性不是保留每句话，而是能从真实状态恢复同一条任务主线。

工具报错就报告真实错误。没有运行过就写「未运行」。诚实地停下来，是可靠 Agent 工作流的一部分。

## 第 16 页

现在才进入沉淀。

只发生一次的目标留在 Prompt。仓库里持续成立的约束进入 Rule。同一类任务要在代表性样例和失败案例上实际成功，并有可重复的回归检查，输入、输出和失败边界也稳定，再写成 Skill。

需要并行时，不是简单说「多开几个 Agent」。要给每个 Subagent 明确输入、范围、交付物和验收方式，并避免几个人同时修改同一位置。

需要自动启动时，再补 Automation 的幂等、去重、超时、失败通知和人工接管。

第一次成功只能证明这个案例做成了。少数成功也可能只是样例过于相似。把未经回归检查的流程直接自动化，等于把尚未发现的假设也一起固化。

## 第 17 页

（计时 4 分钟。先让所有人做基础任务，长期用户再做进阶任务。）

原始需求里「优化」「顺便整理」「确保没问题」都没有可检查含义。

基础任务不是写漂亮提示词，而是把六个缺口补上，判断每项要求属于哪个作用域，并写出能实际观察的证据。

进阶任务要进一步判断：哪些操作有风险，哪里应该暂停，需不需要拆给 Subagent，以及哪一步现在不具备自动化条件。

最后再写一份任务状态快照：主目标、已完成、当前步骤、下一步和阻塞项。假设对话此时中断，另一个 Agent 能否只靠这份快照和当前产物安全继续？

讲评时不评文采，只看六件事：Agent 能不能开始，结果能不能验证，达到什么条件应该停止，中断以后能不能恢复，长期规则、当前任务和运行状态是否放在正确作用域，以及规则变化能否用回归案例评估并删除旧内容。

## 第 18 页

最后五句。

先定义完成，再让 Agent 行动。

把稳定要求放到正确作用域，用行为证据迭代，并定期删减。

让事实进入上下文，让工具接触真实世界。不要让 Memory 和模型常识冒充当前事实。

看测试、diff 和来源，不信完成语气。

失败时缩小问题、修正事实，必要时换一轮干净上下文。

先跑通，再写 Rule、Skill、Subagent 和 Automation。

真正的最佳实践不是让 Agent 显得更自主，而是让它的自主过程更可控、结果更可验证。
