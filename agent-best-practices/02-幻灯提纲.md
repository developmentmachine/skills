# 幻灯提纲

每页只放听众需要看见的内容。口播和动作在 [03-讲稿.md](03-讲稿.md)。

---

## 第 1 页 · 标题

**让 Agent 可靠交付**

从「会用」到「用好」

今天不背提示词。我们完成一次有证据、可审计、范围受控的任务。

---

## 第 2 页 · Prompt 写清楚，就能可靠交付吗

> 修复 `issue.md` 描述的重复提交问题。
> 只修改 `src/` 和必要测试，不改公开 API。
> 修改前后运行现有测试，最后说明改动、测试结果和未验证内容。

Agent 回复：

> 已完成重复提交问题的修复。  
> 优化了状态管理，并补充了边界情况处理。  
> 所有功能均正常。

但我们还不知道：

- 它看了哪些事实？
- 实际改了什么？
- 运行过什么检查？
- 哪些内容没有验证？

**一段像样的回复，不是完成任务的证据。**

Prompt 是任务入口，不是交付系统。

---

## 第 3 页 · 用户 Prompt 不等于模型输入

```text
用户 Prompt
    ↓
Agent 宿主组装模型输入
├─ System / Developer 指令
├─ 对话历史、已加载的 Rule、Skill、Memory
├─ 检索到的事实与当前任务状态
└─ 工具定义与此前的工具结果
    ↓
模型判断下一步
├─ 生成回复
└─ 请求工具 → 宿主执行 → 结果进入下一轮模型输入
```

- **用户 Prompt**：用户提交的任务入口
- **模型输入**：一次调用中模型实际收到的全部内容
- **上下文窗口**：一次调用能够处理的有限容量

模型提出下一步，宿主和工具才会改变真实世界。

---

## 第 4 页 · 先判断该不该交给 Agent

适合交给 Agent，需要三个条件：

1. **可验证**：知道怎样判断结果对不对
2. **可访问**：Agent 能拿到必要事实和工具
3. **可控制**：错误动作可以限制、审批或回退

不满足时：

- 简单确定的步骤：直接用脚本
- 没有事实来源：先补数据
- 不可逆且高风险：保留人工决策

自主程度由风险决定，不由 Agent 看起来多聪明决定。

---

## 第 5 页 · 开始前先写任务契约

```text
目标：最终要改变什么
范围：允许查看和修改什么
事实：以哪些文件、测试或系统为准
约束：不能做什么，哪些不是本次目标
完成：哪些检查通过才算结束
审批：什么动作前必须停下来问
```

模糊的「修一下」让 Agent 猜目标。

任务契约把 Prompt 变成可执行、可停止、可验收的起点。是否做到仍需检查。

---

## 第 6 页 · 不要把所有要求塞进 Prompt

```text
平台 / 组织：权限、安全、合规底线
  └─ 用户：跨项目偏好和默认工作方式
      └─ 项目：架构、命令、事实源、默认验收
          └─ 目录：模块独有约束
              └─ 当前任务：目标、范围、完成、临时例外
                  └─ 运行状态：进度、错误、证据
```

一条要求放在能够准确覆盖它的**最小稳定作用域**。

- 下层可以具体化上层，但不能静默放宽安全边界
- 运行状态会变化，不要写成长期规则
- `AGENTS.md`、Rule、系统配置只是不同产品的载体

---

## 第 7 页 · `AGENTS.md` 已广泛支持，但不是统一入口

- **直接读取项目 `AGENTS.md`**：Codex、Cursor、Hermes、GitHub Copilot
- **可配置读取**：Gemini CLI 默认用 `GEMINI.md`
- **通过入口引用**：Claude Code 用 `CLAUDE.md` 中的 `@AGENTS.md`
- **用户级仍不统一**：各家使用自己的全局规则路径或设置

```text
AGENTS.md       公共项目规则
CLAUDE.md       @AGENTS.md
GEMINI.md       只补 Gemini 差异，或配置读取 AGENTS.md
```

`~/.agents/` 主要是共享 Skill 目录，不是通用的全局规则目录。

加载方式会变化；落地前查文档，配置后检查实际加载结果。

---

## 第 8 页 · 规则文件要迭代，但不能只增不减

```text
重复失败 → 判断机制 → 选择作用域 → 最小修改
        → 行为回归 → 检查加载 → 保留或回退
```

- 没有通用 `version` 字段：用 Git、diff 和评审记录版本
- 课程软预算：根规则尽量少于 200 行
- 更新时删除重复、冲突和过期内容
- 动态事实留在任务或状态；按需流程进入 Skill
- 强制要求交给测试、权限、Hook 或 CI

厂商限制不同：Codex 默认合并 32 KiB；部分产品没有公布硬上限。

**最大长度不是目标，稳定遵循和可验证才是。**

---

## 第 9 页 · 上下文不是越多越好

先建立事实边界：

1. 标出来源和时效：文件、测试、日志、业务系统
2. 网页、邮件、Issue 和日志是数据，不自动成为指令
3. 来源冲突时说明冲突，不静默选择
4. 让 Agent 先调查，再复述当前判断

Memory 可以过期。聊天记录可以污染。模型常识不能替代项目事实。

> 主目标 / 已完成 / 当前步骤 / 下一步 / 阻塞项

关键决定写进项目。改变方向时明确是补充、暂停还是替换。

**连续性不是记住全部对话，而是始终知道正在完成什么。**

---

## 第 10 页 · 自主行动也要分阶段

```text
观察：读事实，复现问题
  ↓
计划：说明要改哪里、怎样验证
  ↓
行动：做一个范围可控的修改
  ↓
检查：测试、diff、日志、来源
  ↺ 未达标：继续或纠偏；高风险：要求暂停
```

简单、可逆、有明确测试：可以直接行动。

范围不清、高风险、不可逆：先计划并等待批准。

外部写操作：执行前重读状态 → 必要时审批 → 幂等或去重 → 执行后重读验证。

## 第 11 页 · 不同机制解决不同问题

- Prompt：本次目标和临时要求
- Rule：持续或按范围生效的约束
- Skill：一类任务的可复用流程
- 工具 / MCP：读取事实和执行动作
- Memory：跨会话保留、但可能过期的状态
- Subagent：隔离上下文或并行调查
- Automation：按时间或事件启动工作

Plugin 在外面负责打包和分发，不负责让结果自动正确。

治理贯穿所有机制：权限、审批、测试、日志和评估。

## 第 12 页 · 主演示：契约不必全写在 Prompt

问题：重复提交保护只记住最近一次请求。

```text
AGENTS.md          项目边界、命令、默认验收和审批
src/AGENTS.md      源码实现约束
tests/AGENTS.md    测试约束
issue.md           当前目标、范围和非目标
测试 / diff        运行状态与验收证据
Prompt             启动任务并补充本次变化
```

开始前先说明：

1. 宿主实际自动加载了哪些规则
2. 哪些文件只是 Agent 后来显式读取
3. 六项契约分别来自哪里

**配置文件存在，不等于已经进入模型输入。**

---

## 第 13 页 · 完成不是一句话，是一条证据链

现场必须看见：

1. 修改前：相关测试失败
2. 调查：读了 Issue、测试和实现
3. 修改：diff 只包含预期范围
4. 修改后：同一测试命令通过
5. 汇报：说明未验证内容和剩余风险

Agent 说「测试通过」不算。

**测试命令的真实输出才算。**

---

## 第 14 页 · 验收只问四件事

1. 它依据了什么事实？
2. 它实际做了什么？
3. 什么证据证明结果正确？
4. 哪些内容仍未验证？

分别检查：

- 事实来源
- 文件和外部动作
- 测试、diff、日志、引用
- 假设、风险和未执行项

---

## 第 15 页 · 跑偏时不要继续加提示词

按顺序恢复：

1. 停止扩大改动
2. 找出缺失事实或错误假设
3. 回退无关改动
4. 缩成一个可验证步骤
5. 上下文已经污染时，新开一轮并带上结论和证据

中断后先对齐主目标、当前状态和下一步，再继续行动。

工具失败时报告真实错误。没有证据时说「未验证」。

不要让 Agent 为了显得完成而补故事。

---

## 第 16 页 · 先跑通，再沉淀

只发生一次：留在本次 Prompt。

仓库里持续成立：写成 Rule。

经过代表性样例、失败案例和回归检查：写成 Skill。

需要隔离或并行：设计 Subagent 的输入、范围、产物和验收。

需要自动启动：再加 Automation、幂等、超时、通知和人工接管。

**第一次成功只是案例，不是标准流程。**

---

## 第 17 页 · 练习

原始需求：

> 帮我优化登录接口，顺便把相关代码整理一下，确保没问题。

基础任务：

- 补全六项任务契约
- 判断每项要求应放在用户、项目、目录还是当前任务层
- 写出至少三项验收证据

进阶任务：

- 指出高风险动作和审批点
- 设计一份公共规则在不同 Agent 中的接入方式
- 说明一次重复失败怎样转化为可回归、可删减的规则变更
- 说明是否需要 Subagent
- 指出哪一步现在不应自动化
- 写一份中断后可恢复的任务状态快照

4 分钟后只看：是否可执行、可验证、可停止、可恢复、正确分层并可维护。

---

## 第 18 页 · 带走

1. **先定义完成，再让 Agent 行动。**
2. **把稳定要求放到正确作用域，用证据迭代并定期删减。**
3. **让事实进入上下文，让工具接触真实世界。**
4. **看测试、diff 和来源，不信自述。**
5. **失败时缩小问题；先跑通，再沉淀和自动化。**

可靠交付 = 清晰目标 + 分层约束 + 权威上下文 + 受控行动 + 客观验证
