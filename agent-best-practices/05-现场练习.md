# 现场演示与练习

## 主持人演示

时长：10 分钟。

目的不是证明某段提示词永远有效，而是展示分层规则、当前任务、运行状态和验证证据怎样组成一次完整工作闭环。

### 演示前准备

1. 把 `examples/login-submit/` 复制到单独的临时目录。
2. 只打开这个临时目录，避免 Agent 读取讲稿和主持人说明。
3. 在临时目录建立 diff 基线，不需要创建提交：

   ```bash
   git init
   git add .
   ```

   演示时同时查看 `git status --short` 和 `git diff`。需要重来时，从原始示例重新复制一份，避免残留改动。

4. 确认临时目录包含根 `AGENTS.md`、`src/AGENTS.md`、`tests/AGENTS.md`、`CLAUDE.md` 和 `.gemini/settings.json`。
5. 确认机器有 Python 3，不需要安装第三方依赖。
6. 在演示目录运行：

   ```bash
   python3 -m unittest discover -s tests -v
   ```

7. 应该看见一个测试通过、一个测试失败。失败用例是：

   ```text
   test_repeat_request_after_another_request_is_rejected
   ```

如果预演时不是这个结果，不要现场继续。先恢复示例目录。

### 给 Agent 的任务

```text
修复 issue.md 描述的重复提交问题。

开始行动前：
1. 说明宿主实际自动加载了哪些指令文件；没有证据时不要声称已经加载。
2. 显式读取 issue.md、相关测试、实现，以及当前工作范围内尚未自动加载的规则文件。
3. 用目标、范围、事实、约束、完成和审批六项复述本次任务，并标出各项来自哪里。发现冲突或关键缺口时先停下来说明。

没有阻塞项时继续完成任务。最后说明：实际加载或读取了什么、改了什么、测试证据是什么、还有什么未验证。
```

### 现场观察顺序

不要只等最终回复。按顺序让听众看：

1. Agent 能否区分「宿主自动加载」和「自己显式读取」。
2. 是否识别根规则、目录规则、`issue.md` 和运行状态各自承担的角色。
3. 是否从多个来源组装出六项任务契约，而不是要求用户重新粘贴完整模板。
4. 修改前是否真实运行测试，并出现预期失败。
5. 是否把问题定位为「只保留最近一个请求 ID」。
6. 修改是否局限在必要范围。
7. 修改后是否运行同一测试命令。
8. 是否展示真实 diff。
9. 最终汇报是否包含未验证内容。

理想修改只需要调整保存已接受 ID 的方式。即使 Agent 给出不同实现，只要公开行为不变、测试通过且范围合理，也按证据评价，不按主持人的预期代码评价。

### Agent 没按预期做时

不要代替它宣布成功。

- 没有先跑测试：要求停止修改，先恢复改动并建立失败基线。
- 声称加载了实际未加载的规则：要求它区分宿主注入和显式读取，并纠正来源说明。
- 没有自动加载嵌套规则：这不是任务失败；显式读取后继续，并用来说明产品差异。
- 改了无关文件：让它解释每项改动与目标的关系，回退无关部分。
- 测试仍失败：让它只分析失败输出，不允许继续扩大修改。
- 安装了依赖：指出它违反任务契约；恢复目录后重新演示。
- 最终只说「测试通过」：要求展示实际命令和输出。
- 上下文反复自我解释：新开一轮，只提供已确认的任务契约、适用规则、当前 diff 和真实失败输出。

现场出现一次恢复动作，比一次完美演示更能说明课程主题。

### 规则迭代微演示

从现场出现的一个偏差出发，不要立即向 `AGENTS.md` 追加一句更强硬的话。按顺序判断：

1. **没有加载**：修正文件位置、产品配置或启动目录，规则文字不一定需要改。
2. **规则冲突**：删除或合并冲突项，明确适用作用域。
3. **规则含糊**：用具体动作和可观察结果替换原句，不保留两个近义版本。
4. **单次偶发**：先记录，不升级为长期规则。
5. **重复且代价明确**：做一项最小规则修改，并在 `instruction-evals.md` 增加对应案例。

展示规则 diff，确认变更中既有新增或改写，也检查了应删除的旧内容。版本由 Git 记录；`instructions-owner` 和 `last-reviewed` 只是课程约定，不是标准字段。

重新运行相关 instruction eval，并检查至少一个原本正常的案例没有退化。规则变更没有行为证据时，只能算文字修改，不能算优化完成。

## 听众练习

时长：4 分钟写作，2 分钟讲评。

原始需求：

```text
帮我优化登录接口，顺便把相关代码整理一下，确保没问题。
```

### 基础任务

补全六项任务契约：

```text
目标：
范围：
事实：
约束：
完成：
审批：
```

再列出至少三项最后必须看见的验收证据。

标出契约中的每项要求应该留在当前任务，还是在长期稳定后进入用户、项目或目录层。不要因为这次出现一次，就直接升级成长期规则。

不知道项目细节时，不要编接口名和测试命令。把需要向任务发起人确认的问题写出来。

### 进阶任务

在完成基础任务后，再回答：

1. 哪些动作属于高风险或不可逆操作？
2. 哪些事实必须从真实系统重新读取？来源冲突时怎样处理？
3. 如果项目规则禁止修改认证策略，而当前任务要求「必要时可以直接调整」，Agent 应该怎样处理这个冲突？
4. 团队同时使用 Codex、Cursor、Gemini CLI 和 Claude Code，怎样只维护一份公共项目规则？配置后怎样确认各端确实加载？
5. 某类任务连续两次跳过修改前基线：是否应修改规则？写出最小规则 diff、回归案例，以及应删除或替换的旧内容。
6. 是否需要 Subagent？如果需要，分别给出输入、范围、产物和验收；如果不需要，说明原因。
7. 哪一步目前不应该自动化？缺少什么条件？
8. 假设任务此时中断，写出主目标、已完成、当前步骤、下一步和阻塞项，让下一轮可以安全恢复。

### 讲评标准

只看六件事：

1. **可执行**：Agent 是否知道先调查什么、允许改什么。
2. **可验证**：完成条件是否对应真实证据，而不是「确保没问题」。
3. **可停止**：达到什么条件结束，遇到什么情况暂停并询问。
4. **可恢复**：中断后能否根据状态快照和真实产物继续，而不依赖完整聊天记录。
5. **可分层**：长期规则、当前任务和运行状态是否放在正确作用域。
6. **可维护**：新增规则是否有重复失败证据、回归案例和删除旧内容的计划。

不按提示词长度、语气或术语数量评分。

### 一份合格答案的形状

下面不是标准答案，只用于主持人收束：

```text
目标：
先确认登录接口当前的性能或正确性问题，再修复已经复现的问题。

范围：
允许读取登录调用链、相关测试和日志；确认原因前不做跨模块重构。

事实：
以 Issue、现有测试、可脱敏的性能数据和当前实现为准。
缺少问题现象或基线数据时先提问。

约束：
不改变公开 API，不修改认证策略，不引入新依赖，不处理无关格式化。

完成：
修改前能复现问题；修改后相关测试和回归测试通过；
若目标是性能，使用同一环境和同一方法比较前后数据；展示 diff。

审批：
数据库变更、依赖升级、认证规则变化、生产写操作前暂停。
```

其中“不改变公开 API”和默认测试要求只有在项目长期成立时才进入项目规则；这次的登录问题、调查范围和性能基线仍留在当前任务。测试输出和 diff 属于运行状态与证据，不写进长期规则。

跨工具时可把公共项目规则放进 `AGENTS.md`：Codex 和 Cursor 直接读取；Gemini CLI 配置 `context.fileName`；Claude Code 用 `CLAUDE.md` 中的 `@AGENTS.md` 引入。合格答案还应说明怎样在各产品中查看或验证实际加载内容，而不是只创建文件。

合格的验收证据可以包括：

- 修改前的问题复现或基线数据；
- 实际 diff 和变更文件列表；
- 修改后同一检查方法的结果；
- 未运行的检查、未覆盖环境和剩余风险。

## 课后扩展

让听众选一项最近真实完成过的工作：

1. 写出六项任务契约；
2. 标出其中哪些只属于当前任务，哪些可能成为用户、项目或目录级默认；
3. 保存执行记录和验收证据；
4. 第二次做同类任务时复用；
5. 补充不同输入和失败案例，建立可重复的回归检查；
6. 用 Git diff 评审规则变更，删除重复、冲突和过期内容；
7. 再判断是否写成 Rule、Skill 或 Automation。
