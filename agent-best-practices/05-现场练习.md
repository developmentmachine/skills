# 现场演示与练习

## 主持人演示

时长：12 分钟。

目的不是证明某段提示词永远有效，而是展示一次完整、可复核的 Agent 工作闭环。

### 演示前准备

1. 把 `examples/login-submit/` 复制到单独的临时目录。
2. 只打开这个临时目录，避免 Agent 读取讲稿和主持人说明。
3. 在临时目录建立 diff 基线，不需要创建提交：

   ```bash
   git init
   git add .
   ```

   演示时同时查看 `git status --short` 和 `git diff`。需要重来时，从原始示例重新复制一份，避免残留改动。

4. 确认机器有 Python 3，不需要安装第三方依赖。
5. 在演示目录运行：

   ```bash
   python3 -m unittest discover -s tests -v
   ```

6. 应该看见一个测试通过、一个测试失败。失败用例是：

   ```text
   test_repeat_request_after_another_request_is_rejected
   ```

如果预演时不是这个结果，不要现场继续。先恢复示例目录。

### 给 Agent 的任务

```text
修复 issue.md 描述的重复提交问题。

任务契约：
- 目标：同一个 request_id 在一次 SubmissionGuard 会话中只能被接受一次。
- 范围：只修改 src/ 和必要测试；不要修改公开 API。
- 事实：以 issue.md、现有实现和现有测试为准。不要根据问题标题猜实现。
- 约束：不要安装依赖，不做无关重构，不删除测试。
- 完成：修改前运行现有测试复现失败；修改后运行同一条命令并全部通过；最后展示 diff。
- 审批：需要安装依赖、删除文件或扩大范围时，先停下来问。

最后说明：你读取了什么、改了什么、测试证据是什么、还有什么未验证。
```

### 现场观察顺序

不要只等最终回复。按顺序让听众看：

1. Agent 是否先读取 `issue.md`、测试和实现。
2. 修改前是否真实运行测试，并出现预期失败。
3. 是否把问题定位为「只保留最近一个请求 ID」。
4. 修改是否局限在必要范围。
5. 修改后是否运行同一测试命令。
6. 是否展示真实 diff。
7. 最终汇报是否包含未验证内容。

理想修改只需要调整保存已接受 ID 的方式。即使 Agent 给出不同实现，只要公开行为不变、测试通过且范围合理，也按证据评价，不按主持人的预期代码评价。

### Agent 没按预期做时

不要代替它宣布成功。

- 没有先跑测试：要求停止修改，先恢复改动并建立失败基线。
- 改了无关文件：让它解释每项改动与目标的关系，回退无关部分。
- 测试仍失败：让它只分析失败输出，不允许继续扩大修改。
- 安装了依赖：指出它违反任务契约；恢复目录后重新演示。
- 最终只说「测试通过」：要求展示实际命令和输出。
- 上下文反复自我解释：新开一轮，只提供任务契约、当前 diff 和真实失败输出。

现场出现一次恢复动作，比一次完美演示更能说明课程主题。

## 听众练习

时长：6 分钟写作，2 分钟讲评。

原始需求：

```text
帮我优化登录接口，顺便把相关代码整理一下，确保没问题。
```

### 基础任务

补全六项任务契约：

```text
目标：
范围：
事实：
约束：
完成：
审批：
```

再列出至少三项最后必须看见的验收证据。

不知道项目细节时，不要编接口名和测试命令。把需要向任务发起人确认的问题写出来。

### 进阶任务

在完成基础任务后，再回答：

1. 哪些动作属于高风险或不可逆操作？
2. 哪些事实必须从真实系统重新读取？来源冲突时怎样处理？
3. 是否需要 Subagent？如果需要，分别给出输入、范围、产物和验收；如果不需要，说明原因。
4. 哪一步目前不应该自动化？缺少什么条件？
5. 假设任务此时中断，写出主目标、已完成、当前步骤、下一步和阻塞项，让下一轮可以安全恢复。

### 讲评标准

只看四件事：

1. **可执行**：Agent 是否知道先调查什么、允许改什么。
2. **可验证**：完成条件是否对应真实证据，而不是「确保没问题」。
3. **可停止**：达到什么条件结束，遇到什么情况暂停并询问。
4. **可恢复**：中断后能否根据状态快照和真实产物继续，而不依赖完整聊天记录。

不按提示词长度、语气或术语数量评分。

### 一份合格答案的形状

下面不是标准答案，只用于主持人收束：

```text
目标：
先确认登录接口当前的性能或正确性问题，再修复已经复现的问题。

范围：
允许读取登录调用链、相关测试和日志；确认原因前不做跨模块重构。

事实：
以 Issue、现有测试、可脱敏的性能数据和当前实现为准。
缺少问题现象或基线数据时先提问。

约束：
不改变公开 API，不修改认证策略，不引入新依赖，不处理无关格式化。

完成：
修改前能复现问题；修改后相关测试和回归测试通过；
若目标是性能，使用同一环境和同一方法比较前后数据；展示 diff。

审批：
数据库变更、依赖升级、认证规则变化、生产写操作前暂停。
```

合格的验收证据可以包括：

- 修改前的问题复现或基线数据；
- 实际 diff 和变更文件列表；
- 修改后同一检查方法的结果；
- 未运行的检查、未覆盖环境和剩余风险。

## 课后扩展

让听众选一项最近真实完成过的工作：

1. 写出六项任务契约；
2. 保存执行记录和验收证据；
3. 第二次做同类任务时复用；
4. 补充不同输入和失败案例，建立可重复的回归检查；
5. 再判断是否写成 Rule、Skill 或 Automation。
