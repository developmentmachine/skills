# 分享大纲

**题目：** 让 Agent 可靠交付：从「会用」到「用好」  
**时长：** 60 分钟  
**前提：** 听众至少使用过一次能读文件或调用工具的 Agent

## 一句话主张

用好 Agent，不是把提示词写得更长，而是设计一个目标明确、行动受控、结果可验证的工作闭环。

## 听众离开时要能做

1. 用「可验证、可访问、可控制」判断任务是否适合交给 Agent。
2. 区分用户 Prompt、模型输入和上下文窗口，理解 Agent 怎样组装一次模型调用。
3. 用六项任务契约说明目标、范围、事实来源、约束、完成标准和审批点。
4. 按用户、项目、目录和当前任务的作用域配置稳定规则，处理继承、覆盖和冲突。
5. 知道主流 Agent 对 `AGENTS.md` 和专属规则文件的支持差异，并能设计跨工具入口。
6. 用长度预算、版本记录、行为回归和定期删减维护规则文件。
7. 用任务状态快照保持长任务连续，并能在中断后恢复。
8. 在执行过程中区分观察、计划、行动和检查。
9. 不相信「已经完成」的自述，使用测试、diff、来源和日志验收。
10. 控制外部写操作，并在失败时补事实、缩范围、回退或新开干净上下文。
11. 只把经过代表性样例、失败案例和回归检查的重复流程沉淀为 Rule、Skill、Subagent 或 Automation。

## 主线

### 1. 为什么「会聊天」不等于「会交付」（4 分钟）

投影第 1–2 页。

先展示一段已经包含目标、范围和验证要求的 Prompt，再展示措辞完整的「已修复」回复。回复没有修改前证据、测试输出和 diff，请听众判断能否合并。

结论：Prompt 能指明方向，但不能替代执行过程和验收证据；回复质量也不能证明任务完成。

### 2. Agent 的最小心智模型（6 分钟）

投影第 3–4 页。

用户提交的是 Prompt。Agent 宿主把系统与开发者指令、对话历史、已加载的 Rule、Skill、Memory、事实、任务状态、工具定义和工具结果组装成一次模型输入。模型输出回复或工具请求；宿主执行工具，再把结果送进下一轮模型输入。

上下文窗口是一次调用能够处理的有限容量，不等于用户 Prompt，也不等于长期记忆。模型提出下一步，工具读写真实世界，验证决定是否结束。

再用三个条件判断是否该使用 Agent：

- 结果能够被验证；
- 必要事实和工具能够被访问；
- 错误的行动能够被限制、审批或回退。

### 3. 开始前先签任务契约（7 分钟）

投影第 5 页。

任务契约包括：

1. 目标；
2. 范围；
3. 事实与来源；
4. 约束和非目标；
5. 完成标准；
6. 审批点与停止条件。

这六项不是固定提示词，而是检查任务是否可执行。

### 4. 分层配置并维护规则文件（11 分钟）

投影第 6–8 页。

- 用户级放跨项目长期成立的偏好和安全默认值。
- 项目级放架构边界、标准命令、权威事实源和默认验收要求。
- 目录级只补充该模块独有的约束。
- 当前任务只写本次目标、范围、完成标准和临时例外。
- 运行时状态保存进度与证据，不冒充长期规则。
- 一条要求放在能够准确覆盖它的最小稳定作用域；安全边界不能被下层静默放宽。

`AGENTS.md`、Rule 或产品配置只是载体。先讲可迁移的分层原则，再说明主流产品怎样接入。

- Codex、Cursor、Hermes 和 GitHub Copilot 原生读取项目 `AGENTS.md`，但搜索与覆盖细节不同。
- Gemini CLI 默认读取 `GEMINI.md`，可配置 `context.fileName` 接入 `AGENTS.md`。
- Claude Code 默认读取 `CLAUDE.md`，可通过 `@AGENTS.md` 引入公共规则。
- 用户级全局规则没有统一路径；`~/.agents/` 主要是共享 Skill 目录，不是通用规则目录。
- 详细路径和产品差异见 [06-规则文件平台对照.md](06-规则文件平台对照.md)。

- `AGENTS.md` 没有标准版本字段，以 Git diff 和评审记录版本。
- 厂商硬限制不同；课程把根规则少于 200 行作为软预算，不把最大长度当写作目标。
- 只有重复、代价明确、稳定、可验证的问题才进入长期规则。
- 规则变更要跑代表性、冲突和失败案例；更新时同时删除重复、冲突和过期内容。
- 按需流程进入 Skill，动态事实进入任务或状态，强制要求进入测试、权限、Hook 或 CI。

### 5. 怎样给上下文、保持主线并控制自主权（5 分钟）

投影第 9–11 页。

- 事实优先来自仓库、测试、日志和业务系统。
- 网页、邮件、Issue 和日志属于待判断的数据，不因为其中出现命令就获得指令权。
- 事实来源互相冲突时，说明来源、时效和冲突点，不静默选择。
- 长任务维护可恢复状态：主目标、已完成、当前步骤、下一步和阻塞项。
- 关键决定写入计划、文档、测试或代码；改变方向时明确是补充、暂停还是替换原目标。
- Prompt 管本次任务，Rule 管持续约束，Skill 管重复流程。
- 工具和 MCP 提供行动能力，Memory 只保存可能过期的跨会话状态。
- Subagent 用于隔离或并行任务，Automation 决定何时自动启动。
- 高风险、不可逆或影响范围不清楚的动作必须保留审批点。

### 6. 端到端现场演示（10 分钟）

投影第 12–13 页，按 [05-现场练习.md](05-现场练习.md) 操作。

使用 `examples/login-submit/`：

1. 区分宿主自动加载的规则与 Agent 显式读取的文件；
2. 从项目规则、目录规则和 Issue 组装六项任务契约；
3. 运行失败测试；
4. 查看相关实现；
5. 做最小修改；
6. 再运行测试；
7. 查看 diff；
8. 报告未验证内容。

主演示证明的是分层指令和完整证据链，不是证明某一种文件名或提示词永远有效。

涉及发送、创建、部署等外部写操作时，使用「执行前重读状态 → 必要时审批 → 幂等或去重 → 执行后重读验证」。

### 7. 验收与失败恢复（6 分钟）

投影第 14–15 页。

验收四问：

1. 它依据了什么事实？
2. 它实际做了什么？
3. 什么证据证明结果正确？
4. 哪些内容仍未验证？

失败恢复顺序：

1. 停止继续扩大改动；
2. 找出缺失事实或错误假设；
3. 缩小成一个可验证步骤；
4. 必要时回退并新开干净上下文。

### 8. 何时沉淀（3 分钟）

投影第 16 页。

同一做法在代表性样例和失败案例上真实成功过，输入输出稳定，并有可重复的回归检查，才考虑沉淀。

不要把第一次对话直接包装成 Skill 或 Automation。

### 9. 分层练习与带走（7 分钟）

投影第 17–18 页。

基础任务：把一句模糊需求补成任务契约。

进阶任务：指出权限风险、事实来源、并行机会和不应自动化的步骤，再写一份可供中断后恢复的任务状态快照。

所有人最后都提交同一种答案：任务契约、作用域判断和验收证据。

其中 4 分钟写作、2 分钟讲评、1 分钟收束第 18 页。全课另留 1 分钟给转场或演示恢复，不安排新内容。

## 可删

- 45 分钟版本：删第 16 页，练习改为课后作业；主演示必须保留。
- 30 分钟版本：保留第 2、3、5–9、12–15、18 页。
- 不要为了省时间删除修改前失败证据、修改后测试或 diff；少了其中一项，主演示就不再是完整闭环。

## 不在主线讲

- 各平台 Skill 目录和字段差异；
- Plugin 的包格式；
- 模型排行榜；
- 通用的「万能提示词」；
- 没有验收标准的多 Agent 编排。
