# Agent 规则文件平台对照

核对记录：2026-10-05；Claude Code 的加载方式与长度限制、用户级与项目级规则的冲突处理于 2026-10-08 补核，Codex 官方页面本次连接失败，其冲突顺序待验证。产品行为可能变化，授课前应重新检查官方文档。

## 先记住结论

- 项目级 `AGENTS.md` 已经被 Codex、Cursor、Hermes 和 GitHub Copilot 原生支持。
- Gemini CLI 默认读取 `GEMINI.md`，但可以配置为读取 `AGENTS.md`。
- Claude Code v2.1.277 起支持直接读取 `AGENTS.md`；默认是否加载取决于项目中的 Claude 专属规则文件和 `Project instructions` 设置。旧版或不支持的会话仍可通过 `CLAUDE.md` 引入。
- 用户级全局规则没有统一目录。`~/.agents/` 主要是多款产品共同使用的 Skill 目录，不是通用的全局 `AGENTS.md` 目录。
- 项目规则并不在所有 Agent 中都优先于用户规则。先确认实际加载的文件，再按产品的冲突处理规则判断；加载在后不一定代表覆盖在前。

不要把「文件存在」等同于「当前 Agent 已加载」。文件名、搜索范围、合并顺序和覆盖规则都由宿主产品决定。

## 推荐的跨工具项目结构

```text
repo/
├── AGENTS.md          # 跨工具共享的项目规则
├── CLAUDE.md          # 可选兼容入口，内容可为 @AGENTS.md
└── src/
    └── AGENTS.md      # 仅在确认所用产品支持嵌套规则时使用
```

Gemini CLI 可以在 `settings.json` 中加入：

```json
{
  "context": {
    "fileName": ["AGENTS.md", "GEMINI.md"]
  }
}
```

公共规则只写一份。`CLAUDE.md`、`GEMINI.md` 或产品专属规则只补充该产品确实需要的差异，不要复制整份内容，否则更新后容易互相冲突。

课程中的可运行示例见 [`examples/login-submit/`](examples/login-submit/)。它同时包含根规则、`src/` 与 `tests/` 的目录规则、Claude 入口和 Gemini 配置。

## Codex

- 原生读取 `AGENTS.md`。
- 用户级默认规则：`$CODEX_HOME/AGENTS.md`，`CODEX_HOME` 默认是 `~/.codex`。
- 项目中从仓库根向当前工作目录逐层读取 `AGENTS.md`；更接近当前目录的内容更具体。用户级与项目级冲突时的覆盖顺序，本次官方页面复核待验证。
- 同一目录优先选择 `AGENTS.override.md`，否则选择 `AGENTS.md`，再查配置的备用文件名；每个目录最多加载一份，不是把 override 与原文件叠加。
- `/init` 可以生成当前目录的起始文件。

官方文档：[Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md)

## Cursor

- 原生读取项目根和子目录中的 `AGENTS.md`。
- 父目录和嵌套规则会组合，更具体的子目录规则优先。
- 需要路径匹配、手动启用或元数据时，使用 `.cursor/rules/*.mdc`。
- 跨项目个人默认值使用 Cursor 的 User Rules；官方文档没有把 `~/.agents/AGENTS.md` 定义为全局入口。

官方文档：[Rules](https://cursor.com/docs/rules)

## Gemini CLI

- 默认上下文文件是 `GEMINI.md`。
- 用户级默认规则：`~/.gemini/GEMINI.md`。
- 项目根、工作区路径和访问到的子目录可以分层发现 `GEMINI.md`。
- `context.fileName` 可以改成一个文件名或文件名列表，因此可以接入 `AGENTS.md`。
- `/memory show` 用于查看已拼接的上下文，修改文件后可用 `/memory reload` 重新加载。

官方文档：[Provide context with GEMINI.md files](https://geminicli.com/docs/cli/gemini-md/)

## Hermes Agent

- 原生读取项目中的 `AGENTS.md`，并逐步发现子目录规则。
- Hermes 专属的 `.hermes.md` 或 `HERMES.md` 优先级更高。
- 项目上下文类型采用「首个匹配类型生效」：存在更高优先级的 Hermes 文件时，不能假设 `AGENTS.md` 仍会同时加载。
- 全局身份与表达风格使用 `$HERMES_HOME/SOUL.md`；它不等于项目规则。
- `AGENTS.override.md` 可用于个人、目录级覆盖，通常应加入忽略列表。

官方文档：[Context Files](https://hermes-agent.nousresearch.com/docs/user-guide/features/context-files)

## GitHub Copilot

- GitHub 的仓库规则说明支持一个或多个 `AGENTS.md`，离目标文件最近的规则优先；不要把这条说明当成所有 Copilot 产品形态的统一覆盖顺序。
- Copilot 专属的仓库级规则放在 `.github/copilot-instructions.md`。
- 路径级专属规则放在 `.github/instructions/**/*.instructions.md`。
- Copilot CLI 的用户级规则放在 `~/.copilot/copilot-instructions.md`。
- Cloud Agent、Code Review、IDE 和 CLI 支持面不完全相同，授课或落地时要说明具体产品形态。

官方文档：[Adding repository custom instructions](https://docs.github.com/copilot/customizing-copilot/adding-repository-custom-instructions-for-github-copilot)、[Adding custom instructions for GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-custom-instructions)

## Claude Code

- v2.1.277 起支持直接读取项目 `AGENTS.md`。默认在工作目录及上层没有 `CLAUDE.md`、`.claude/CLAUDE.md` 或 `CLAUDE.local.md` 时加载；用户级和组织托管的 `CLAUDE.md` 不阻止这个回退。
- 在 `/config` 的 `Project instructions` 中可以选择只读 Claude 文件、只读 `AGENTS.md` 或同时读取；配置后用 `/memory` 检查实际加载结果。v2.1.280 之前，直接读取的 `AGENTS.md` 不会显示在 `/memory` 和 `/context` 中。
- 旧版、禁用了读取 `AGENTS.md` 的内置插件等不支持的会话，可以创建 `CLAUDE.md`，用下面一行复用公共规则：

```markdown
@AGENTS.md
```

- 用户级默认规则放在 `~/.claude/CLAUDE.md`。
- 项目级还可以使用 `./CLAUDE.md` 或 `./.claude/CLAUDE.md`。保留 `@AGENTS.md` 兼容入口不等于原生自动加载目录级 `AGENTS.md`，嵌套规则仍需按所选模式检查。
- 直接读取项目 `AGENTS.md` 不代表支持 `.agents/skills/`；不要把规则文件与 Skill 目录混为一谈。

官方文档：[How Claude remembers your project](https://code.claude.com/docs/en/memory) 的 `AGENTS.md` 章节；发布记录：[CHANGELOG.md](https://github.com/anthropics/claude-code/blob/2bfb629dfaff0c8318047a4beb93cf1dc5b58b18/CHANGELOG.md) 的 `2.1.277`、`2.1.281`。

## 用户级规则为什么不能只放一处

当前没有一份所有产品都会自动读取的用户级规则文件：

```text
Codex       ~/.codex/AGENTS.md
Gemini CLI  ~/.gemini/GEMINI.md
Claude Code ~/.claude/CLAUDE.md
Copilot CLI ~/.copilot/copilot-instructions.md
Hermes      $HERMES_HOME/SOUL.md（身份与风格）
Cursor      User Rules
```

如果需要跨产品维护，应该先确定一份自己的权威源，再通过各产品支持的引用、同步或生成方式接入。同步机制必须可检查；不要假设软链接、导入语法或云端同步在所有产品中都有效。

## 用户级与项目级规则冲突时，谁优先

**没有跨 Agent 通用的「项目根 `AGENTS.md` 高于用户级规则」结论。** 用户主目录的 dot 目录只是存放位置，不决定指令权限；不少产品的用户级入口也不叫 `AGENTS.md`。

先区分三件事：

1. **文件选择**：同一目录的多个候选文件，是只选一份，还是同时加载？
2. **加载与合并**：用户、项目、子目录内容是否都进入上下文，以什么顺序进入？
3. **冲突处理**：产品是否明确规定谁覆盖谁？不能仅凭「后加载」推断「优先级更高」。

| 产品 / 形态 | 用户级入口 | 与项目规则如何组合 | 冲突时能确认的结论 |
| --- | --- | --- | --- |
| Codex | `$CODEX_HOME/AGENTS.md`，默认 `~/.codex/AGENTS.md`；同目录 override 优先 | 用户级在前，项目根到当前工作目录在后 | 待验证：需复核官方页面是否明确后面的、更具体的项目规则覆盖用户级冲突内容；本次页面连接失败，不将这一顺序写成已确认结论。[1] |
| Cursor Agent（Chat） | Customize → Rules 中的 User Rules | 所有适用规则合并；项目 `AGENTS.md` 是 `.cursor/rules` 的简化替代入口 | 官方列出 Team Rules > Project Rules > User Rules；嵌套 `AGENTS.md` 中更具体的内容优先。不能把 Team Rules 也归入可被项目覆盖的用户默认值。[2] |
| Gemini CLI | 默认 `~/.gemini/GEMINI.md`，文件名可配置 | 全局 → 环境 / 工作区 → 按工具访问发现的局部上下文，内容拼接 | 文档明确加载顺序，但没有给出这些自然语言指令的确定覆盖规则；「项目必定覆盖用户」待验证。`settings.json` 的配置优先级不能代替上下文文件的冲突规则。[3] |
| Hermes Agent | `$HERMES_HOME/SOUL.md`，默认 `~/.hermes/SOUL.md` | 全局身份文件独立加载；项目上下文先选文件类型，再合并目录链 | 项目目录链内更具体的规则优先；`SOUL.md` 与项目规则冲突时的统一裁决待验证。文档未将 `~/.hermes/AGENTS.md` 定义为通用全局入口。[4] |
| GitHub Copilot 的通用自定义指令说明 | GitHub.com 的 Personal instructions，不是本机 dot 目录文件 | 所有相关指令进入上下文；各形态支持范围不同 | 官方列出 Personal > Repository > Organization；仓库内为路径级专属规则 > 仓库级专属规则 > `AGENTS.md` 等 Agent 指令。这不是「项目总比个人优先」，也不能直接套到 CLI。[5] |
| GitHub Copilot CLI | 默认 `~/.copilot/copilot-instructions.md` 及 `~/.copilot/instructions/**/*.instructions.md` | 适用的用户级、仓库级与 Agent 指令合并，并去除部分相同副本 | CLI 专属文档明确没有定义这些文件之间的通用覆盖顺序；不要套用 GitHub.com 的个人指令排序。[6] |
| Claude Code | `~/.claude/CLAUDE.md`、`~/.claude/rules/` | 用户级在前，项目级在后；已发现的规则拼接，项目 `AGENTS.md` 是否加入取决于加载模式 | 官方明确拼接不等于覆盖；用户规则与项目规则冲突时，Claude 可能采用任意一方。应消除冲突，不能保证项目优先。[7] |

表中 `>` 表示来源间的冲突优先级，不表示模型一定遵守，也不表示后者的全部内容失效。

### 用无副作用的冲突用例核对

不要拿真实的构建、发布或删除操作测试优先级。可以在隔离测试环境中设置两条仅影响输出的规则：

```text
用户级规则：最终回复末尾输出 USER_MARKER
项目根规则：最终回复末尾只输出 PROJECT_MARKER，不输出 USER_MARKER
```

先确认两份文件都已加载，再观察输出、加载记录和冲突提示。之后增加一条不冲突的用户偏好，检查它是否仍然适用；再单独测试子目录规则和同目录 override。没有文档保证的产品，即使一次选择了项目标记，也不能据此宣称「项目必定覆盖用户」。

Codex 的用户级 → 项目根 → 当前目录文件链可以作为加载顺序示例，但本次未能连接官方页面，具体冲突覆盖顺序待验证。[1]

### 维护和验证

- 把用户层写成跨项目默认值，把项目层写成仓库内明确约定；对于没有确定覆盖规则的产品，主动消除冲突，不靠重复写「必须」争取优先级。
- 权限、审批和安全边界不能只靠一份用户级 Markdown 保证，也不能把项目文件的一句例外当成修改权限的授权；需要由权限设置、沙箱、审批、Hook 或 CI 落实。
- 验证时先记录产品、版本、启动目录、加载模式和实际文件，再用无副作用的冲突用例观察行为。Gemini CLI 可用 `/memory show` 查看拼接内容；Claude Code 可用 `/memory` 或 `/context` 查看加载项；Copilot CLI 可用 `/instructions` 查看发现并启用的文件。一次回答的选择不能证明存在稳定覆盖机制。[3][6][7]
- 分别测「不冲突时是否同时生效」「冲突时如何选择」「子目录规则是否加载」「同目录 override 是否替换原文件」。只在临时测试环境操作，不为验证而修改真实用户全局规则。

## 长度限制不是一个统一数字

- **Codex**：项目规则链默认最多读取 32 KiB，可通过 `project_doc_max_bytes` 调整；达到上限后停止加入后续内容。
- **Cursor**：官方 `AGENTS.md` 文档没有公布固定字符或字节上限。
- **Gemini CLI**：官方没有公布 `GEMINI.md` 的固定总长度上限；建议保持聚焦。导入默认最多嵌套 5 层。
- **Hermes**：每份上下文文件使用 `context_file_max_chars`；未显式设置时随模型上下文变化，最低 20,000、最高 500,000 字符，超出后保留文件头尾并标记截断。
- **GitHub Copilot**：官方没有公布 `AGENTS.md` 的硬上限，只建议简短、可执行。「不超过两页」是生成 Copilot 仓库说明时的建议，不是 `AGENTS.md` 格式限制。
- **Claude Code**：官方建议每份规则控制在 200 行以内；超过 4 MiB 的文件会被跳过。通过 `@AGENTS.md` 导入的内容同样占用上下文。依据：[How Claude remembers your project](https://code.claude.com/docs/en/memory) 的 `My CLAUDE.md is too large` 章节。

课程采用跨工具的**软预算**：根规则尽量少于 200 行，只保留每次都值得加载的稳定要求。不要把厂商最大值当成写作目标。还要检查用户、项目和目录规则合并后的总量，而不只看单个文件。

内容增长时优先：

1. 删除模型可从代码直接得出的描述；
2. 删除重复、冲突和过期规则；
3. 把模块规则下沉到对应目录；
4. 把按需流程移到 Skill；
5. 把动态事实移到任务、系统查询或状态快照；
6. 把必须强制执行的要求移到测试、权限、Hook 或 CI。

## 是否支持版本

`AGENTS.md` 是普通 Markdown，没有标准的 `version` 字段、Schema 或 SemVer 语义。自行写入 `version: 2.1` 只是一段文本，除非另有程序读取，否则不会改变加载行为。

推荐使用：

- Git commit、diff、PR 和标签记录真实版本；
- `CODEOWNERS` 或评审规则指定维护责任；
- 可选的 HTML 注释记录负责人和复查日期；
- 架构、命令或平台加载方式变化时触发复查。

例如：

```markdown
<!-- instructions-owner: platform-team -->
<!-- last-reviewed: 2026-10-05 -->
```

这些也是团队约定，不是标准字段。不要维护没有消费方的版本号。

## 规则迭代闭环

```text
观察重复失败
  → 判断应该用指令、Skill，还是确定性控制
  → 选择最小稳定作用域
  → 做一项最小规则变更，同时清理旧规则
  → 跑代表性、冲突和失败案例
  → 检查各产品实际加载结果
  → 评审 diff，保留、修改或回退
```

只有同时满足「重复出现、代价明确、相对稳定、可以验证」的问题，才值得进入长期规则。一次偶发现象先留在任务记录中。

课程示例的 [`instruction-evals.md`](examples/login-submit/instruction-evals.md) 展示了行为回归案例。评估的是 Agent 是否采取了预期行动及其证据，不要求输出固定措辞。

## 验收加载结果

配置完成后至少检查：

1. 当前产品是否真的发现了目标文件；
2. 项目根、子目录和用户层的合并顺序；
3. 是否因为专属文件而跳过公共 `AGENTS.md`；
4. 同一规则是否被重复加载；
5. 云端 Agent、远程会话和本机是否读取相同文件；
6. 仓库自带规则是否来自可信来源。

检查时区分：文件存在、Agent 可以读取、宿主已经自动加载、模型实际遵循。不要用前一项证明后一项。

规则文件只是模型输入的一部分，不是强制执行机制。真正不能违反的权限和安全边界，应由沙箱、权限、审批、Hook 或确定性程序落实。
